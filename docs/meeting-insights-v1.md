# CampBox · Meeting Insights v1 — история и динамика встреч

**Статус:** реализация в отдельной ветке; production НЕ изменён. Не сливать до SQL-миграции, проверки RLS и реального тестового пакета.

## Задача
Отдельные разборы встреч уже содержат баллы, ошибки, рекомендации, голос клиента и маркетинговые выводы. Однако Sales Coach в основной доске считает активности и конверсии, а не качество встреч. Meeting Insights добавляет накопительную аналитику в той же защищённой Sales Board.

## Порядок запуска
1. Проверить код в pull request и сделать резервную копию Supabase.
2. В SQL Editor *существующего* проекта Sales Board выполнить \`migrations/meeting-insights-v1.sql\`. SQL не удаляет существующие таблицы.
3. Проверить RLS под пользователем-менеджером и сотрудником.
4. Выпустить ветку в тестовую публикацию и проверить вход, отображение и импорт.
5. Добавить в инструкции плагина «CampBox | Продажник» обязательный **экспорт JSON** в дополнение к текущей человекочитаемой оценке (см. ниже). Сам плагин **не был обновлён** в этом PR.
6. Только после приемки слить PR / публиковать основной сайт.

## Контракт данных «Продажник» → Sales Board
Разбор остается в принятом формате: scorecard → 6 блоков анализа → саммари / ТЗ.
После него «Продажник» должен выводить **отдельный валидный JSON-блок**, который пользователь копирует в раздел «Добавить оценку встречи».

### Словарь
- meeting_key: уникальный стабильный ключ **одной встречи**; одинаковый ключ обновляет запись того же менеджера.
- meeting_type: DISCOVERY / DEMO / NEGOTIATION / FOLLOW_UP / OTHER.
- assessment.total: 0–100; версия обязательна для сопоставления, coverage 0–100 или null.
- reliability: RELIABLE / PROVISIONAL / INSUFFICIENT_DATA.
- skills: **баллы, не проценты**, максимумы: structure 10, diagnostics 15, pain_priority 20, decision_process 10, personalization 15, objections 10, next_step 15, communication 5.
- errors: коды ошибок (стабильный словарь, а не свободные синонимы).
- marketing: массив анонимизированных тем. Не включать в signal контактные данные, ФИО, цитаты с персональной информацией или транскрипт целиком.
- outcome: UNKNOWN / NEXT_MEETING / PROPOSAL / CONTRACT_SENT / SIGNED / LOST. Меняется в таблице после встречи, НЕ выводится из балла.

### Инструкция для «Продажника»
«В конце каждого разбора сохрани неизменный порядок отчёта и приложи JSON campbox.meeting.v1. Оценки выставляй только по доказанным репликам из транскрибации. Если нельзя надёжно оценить, помечай PROVISIONAL или INSUFFICIENT_DATA, не выдумывай баллы. Не включай ПДн и полный транскрипт. Переноси точный meeting_key при повторном анализе той же встречи. Используй один и тот же словарь навыков, ошибок и маркетинговых тем. Следующий шаг фиксируй отдельно от результата сделки. Если версия оценочной методики меняется, увеличивай assessment.version».

## Методика динамики
- **Хронология:** сохранённые встречи за 30 / 90 / 365 дней или всё время.
- **Надёжный срез:** только RELIABLE и coverage >= 70.
- **Сопоставимость:** один тип встречи, одна версия методики; при фильтре «Все» берётся группа последней надёжной встречи.
- **Δ:** среднее последних 3 минус среднее предыдущих 3. Пока сопоставимых встреч меньше 6, вывести BASELINE вместо «роста».
- **Навыки:** средние полученные баллы / максимумы по пунктам шкалы.
- **Повторяющиеся ошибки:** частота кодов в трёх последних сопоставимых встречах.
- **Маркетинг:** частота тематических инсайтов за выбранный период; не выдавать единичную реплику за отраслевой тренд.
- **Результат:** поле outcome редактируется отдельно от рейтинга. Показатель подписано/(подписано+потеряно) рассчитывается по завершённым сделкам. Не называть это конверсией всех встреч или атрибуцией договора.

## Ограничения текущей версии
- Данные из чатов ChatGPT/плагина пока **не поступают автоматически**. Есть копирование одного JSON, сохранение и ручной бэкфилл старых баллов. Следующий этап — серверный защищённый webhook/API импорта с идемпотентностью и обязательной авторизацией; anon key недостаточен для серверной записи.
- Для связки с договором необходим надёжный клиентский / deal ID из CRM или Sales Board. Связка по имени лагеря недостаточна и сейчас НЕ реализована.
- Ручные записи PROVISIONAL не влияют на тренд качества, пока их не заменить подтверждёнными оценками.
- История ограничена первыми 1000 записей; если масштаб больше, добавить пагинацию перед запуском на весь отдел.
- Не хранить полные транскрибации и персональные данные в этой таблице. Перед запуском оценить обработку производных данных и требуемые договоры/локализацию по 152-ФЗ.
- Автоматический разбор всех старых чатов и ретроспективная привязка к договорам не реализованы.

## Минимальные критерии QA
1. Активный сотрудник видит только собственные встречи; руководитель — свою и общую историю; неактивный пользователь не может читать/изменять.
2. Повторный meeting_key того же сотрудника не создаёт дубликат.
3. При 0–5 сопоставимых встречах Δ = BASELINE; при 6+ — корректный сдвиг средних 3 к 3.
4. Смешение DEMO и DISCOVERY, разных assessment.version, ненадёжных и неполных транскрибаций не искажает Δ.
5. Вручную созданная встреча показывается в истории и не включается в надёжный тренд.
6. Переключение результата встречи переживает обновление страницы; пропуски данных не превращаются в нули навыков.
7. Длинный текст экранируется; недопустимые scores / даты / форматы отклоняются.
8. Dashboard не ломает основной план-факт, зарплату, контрактинг, фильтры, мобильную версию, экспорты.
9. Проводится QA на мобильной ширине, под разными ролями, до переключения production.
